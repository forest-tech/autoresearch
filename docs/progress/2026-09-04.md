## 4GPUを用いた並列実験

### 目的

HPC環境では **1 node = 4 GPU** のため、1GPUにつき1候補実験を割り当て、4つの候補を並列に評価する。

各ラウンドでは、現在の最良モデル（accepted commit）を共通の開始点として4つの候補を生成・学習し、`val_bpb` が最も良い候補のみを次のラウンドに採用する。

```text
accepted commit
      │
 ┌────┼────┬────┐
GPU0 GPU1 GPU2 GPU3
 │    │    │    │
実験  実験  実験  実験
 └────┼────┴────┘
      │
  最良候補を採用
      │
次の accepted commit
```

### 4つの直列探索を独立に走らせない理由

単純に4GPUそれぞれで独立した直列探索を行うと、各探索のGit履歴や採用済み実験が別々に分岐する。

```text
base
├─ GPU0: A → B → C
├─ GPU1: D → E → F
├─ GPU2: G → H → I
└─ GPU3: J → K → L
```

この方式では、

* 各探索で基準となるモデルが異なり、実験結果を比較しにくい
* 同じ実験を複数の探索が重複して試す可能性がある
* Gitブランチが複数に分岐し、最終的な統合が複雑になる
* 「現在の最良設定」が複数存在する状態になる

という問題がある。

そのため、**探索自体を4本に分けるのではなく、1本の探索の各ステップで4候補を並列評価する**方式を採用する。

### Git管理

各候補は `git worktree` を用いて独立した作業ディレクトリで実行する。

Worker側ではGitのcommit操作を行わず、候補の変更と評価結果のみを生成する。

最終的な

* 候補の選択
* `train.py` への変更適用
* `git commit`
* `results.jsonl` への記録

は1つの coordinator が担当する。

これにより、並列実験を行ってもGit履歴は

```text
baseline
   ↓
round 1 best
   ↓
round 2 best
   ↓
round 3 best
```

のように、採用された実験だけを一直線に管理できる。
