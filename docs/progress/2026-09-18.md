## NOTES

### `codex exec` の出力の揺れについて

- `codex exec` には、 `--seed` オプションは 2026/09/18 現在、存在しない
- `seed` のように、出力を固定できるようなオプションが無いため、出力ごとに `codex exec` すなわちハイパラ調整の提案はある程度揺れる様になる
  - `train.py` の `seed = 42` (default) で固定できるため、学習の揺れはある程度制御できる
  - 学習は step 数で終了するのではなく、wall_time = 300 sec = 5 min で管理しているため、CPU・GPUの調子に多少左右されるため、val_bpb の値は完全に一致はしない
- 他の cli LLM サービスにも seed に相当するものは存在しない

| ツール         |      CLIから生成seed指定 | 同一prompt→同一結果の保証 |
| ----------- | -----------------: | ---------------: |
| Codex CLI   |             確認できない |                ❌ |
| Claude Code |             確認できない |                ❌ |
| Gemini CLI  | CLIオプションとしては確認できない |                ❌ |
| Gemini API  |       **`seed`あり** |    ⚠️ 完全一致の保証とは別 |

- Gemini API には seed パラメータがあり、「デコードに使用するシード」と公式仕様に明記されている
  - https://ai.google.dev/api/generate-content?hl=ja
  - LLMの呼び出しは固定できるが、途中のコマンド出力、ファイル状態、Git状態、外部ツールの結果、モデル側の実装変更などが少しでも違えば、その後のコンテキストが変化して実行経路も変わる可能性が高い

#### 結論

- 制御をするのは難しい
- 今回の設定だと codex はseedによる制御ができないため、事実として codex の出力は揺れることを考慮しておくようにする

### 与える履歴を管理する実験( `history` 系)

#### 結果

 - 履歴全件と1件の結果を比較して、1件のほうが性能が良かったので直感と反する

#### 原因の考察

- 現時点だとデータが少なくて考察できない
- 設定を変えた追加実験の結果を合わせて問題の切り分けをしていく

#### 追加実験の設定

- 同じ履歴を与えた設定ごとの seed の差がどれだけあるかのデータが欲しい
  - negative prompt
		- 画像の分野である
		- 「〜しないでほしい」
	- promptで与える結果にいらない部分が多すぎる
	- discardだけ与える実験(対照実験)
	  - 捨てた方の結果だけを入れる
		- これの傾向が今のやつと同じような感じならばdiscardに引っ張られてる可能性
	- keep だけ与える実験
	  - 結果の補強になる
- プロンプトをJSONL, JSON 形式にする
  - pythonでjsonl, json がいじれるので、この形式にすると制御しやすい
- seed をもう一回やりたい (42, 43 以外)
  - 最終的にseedが5-10くらいでデータを集めて、分散をとりたい
	- ひとまず 3 個で取る
